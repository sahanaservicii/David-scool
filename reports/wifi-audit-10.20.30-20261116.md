**Дата отчёта:** 16.11.2026

  не определить.
- Пароли не подбирались, эксплойты не запускались, прошивки не скачивались, секреты не читались.

**Что сканировалось:** только диапазон **10.20.30.0/24**. Чужие сети не затрагивались.

**Три набора данных, использованных в отчёте:**

## C. Уязвимости и риски

### C1. UDM Pro: есть непрошитая прошивка (`deviceState: updateAvailable`)

- **[ФАКТ]** Неавторизованный `GET /api/system` на 10.20.30.1 отдаёт `"deviceState":"updateAvailable"`.
  Это означает, что установленная прошивка не является последней.
- **[ФАКТ]** В HTML фигурирует суффикс ассетов `?udmpro-3.0.1` и `Last-Modified: Thu, 09 Jan 2025`.
  Это косвенный признак поколения/ветки сборки; **точная версия UniFi OS не установлена** (эндпоинт
  версии `/api/system/version` вернул `401 Unauthorized`).
- **[ВЫВОД]** Непрошитая консоль = консоль без исправлений, вышедших после установленной версии.
  Риск зависит от того, какие именно исправления пропущены; **список CVE для конкретной версии не
  установлен** (нет доступа к бюллетеням вендора в офлайне).
- **Класс риска:** известные уязвимости UniFi OS / UniFi Network / UniFi Protect. Исторический пример
  класса «критичный RCE в UniFi Network» — **Log4Shell (CVE-2021-44228, декабрь 2021)**; он относится
  к продуктам UniFi Network того периода. **Проверить в бюллетенях вендора** (`ui.com/security-advisories`),
  применимо ли это к текущей версии — по данным сканирования **не установлено**.
- **Критичность:** 🟠 средняя–высокая (зависит от пропущенных исправлений; наружная экспозиция не проверена).
- **Что делать:** обновить прошивку через UniFi OS → **Settings → System → Updates**. Перед обновлением —
  бэкап конфигурации. Сверяться с бюллетенями `ui.com/security-advisories`.

### C2. Неавторизованный `GET /api/system` → 200 и утечка метаданных

- **[ФАКТ]** `GET https://10.20.30.1/api/system` без авторизации вернул **200 OK** и тело:
  `{"hardware":{"shortname":"UDMPRO"},"name":"UDM Pro","mac":"D8B370168E1E","directConnectDomain":null,`
  `"deviceState":"updateAvailable","deviceErrorCode":null,"uidb":{...},"debugEnabled":false,`
  `"cloudConnected":false,"isOrHasGatewayInLAN":true,"remoteAccessEnabled":false,"hasInternet":true,`
  `"hasInternetLastChanged":1792890495108,"isSingleUser":false,"isSsoEnabled":false}`
- **Что утекает без входа [ФАКТ]:** модель/hardware-код (`UDMPRO`), отображаемое имя (`UDM Pro`),
  **MAC-адрес консоли** (`D8B370168E1E`), состояние устройства (`updateAvailable`), факт наличия
  интернета (`hasInternet`), состояние облачной привязки (`cloudConnected:false`), флаг удалённого
  доступа (`remoteAccessEnabled:false`), `isSingleUser:false`, `isSsoEnabled:false`, `debugEnabled:false`,
  `isOrHasGatewayInLAN:true`, а также поле `uidb`.
- **[ВЫВОД]** Практическая ценность для атакующего: MAC (используется как идентификатор при
  запросах/пейринге, а также как ключ в консоли), точная модель и признак непрошитой прошивки —
  удобная «разведка» перед подбором вектора. Само по себе чтение не даёт доступа и не меняет состояние.
- **[ВЫВОД]** `isSingleUser:false` → в консоли **заведено более одного аккаунта** (не «единственный
  пользователь»). Это нормально для консоли, но означает, что нужно знать и контролировать **все**
  учётные записи и их права.
- **[ВЫВОД]** `remoteAccessEnabled:false` и `cloudConnected:false` — хорошие признаки: удалённый
  доступ/облако, судя по флагам, выключены. Это снижает наружный риск (но наружная экспозиция
  портов всё равно не проверена).
- **Критичность:** 🟡 низкая–средняя (информационная утечка, не даёт доступа).
- **Что делать:** это штатное поведение многих версий UniFi OS; полностью убрать без вендора нельзя.
  Смягчение — не публиковать консоль наружу (удалённый доступ через VPN/WireGuard), обновляться,
  и понимать, что MAC консоли «виден» в LAN. Регулярно проверять список аккаунтов.

### C3. Самоподписанные TLS-сертификаты

- **[ФАКТ]** TLS-порты шлюза используют TLSv1.3, но **subject и issuer пустые → самоподписанный
  сертификат**. Относится к: **443, 7443, 8443, 8843, 9443, 12443, 12445**.
- **[ВЫВОД]** Самоподписанный сертификат не проверяется клиентом по цепочке доверия → внутри LAN
  возможен MITM при условии, что атакующий уже в сети (ARP/DNS-подмена). Браузеры показывают
  предупреждения, что приучает пользователя их игнорировать.
- **[ФАКТ]** На 443 включён HSTS (`max-age=15552000; includeSubDomains`) и есть заголовки
  `X-Frame-Options: SAMEORIGIN`, `X-Content-Type-Options: nosniff` — это плюс.
- **Критичность:** 🟡 низкая–средняя (внутренний MITM; для домашней сети — терпимо, но не идеально).
- **Что делать:** при наличии домена — выписать нормальный сертификат (Let's Encrypt через UniFi OS);
  если домена нет — зафиксировать отпечаток сертификата и не игнорировать предупреждения.

### C4. Множество HTTP/HTTPS-портов управления, часть — без TLS

- **[ФАКТ]** На 10.20.30.1 открыты (полный список, воспроизводимый): 22, 53, 80, 443, 7441, 7442,
  7443, 7444, 7445, 7446, 7447, 7451, 7550, 7552, 7600, 7888, 8080, 8443, 8843, 8880, 9443, 11083,
  12301, 12443, 12445, 12812, 20201. В широком проходе добавляется **199**.
- **[ФАКТ]** `:80` → `301` на `https://10.20.30.1/` (`Server: nginx`).
- **[ФАКТ]** **`:8080` и `:8880` отдают plain HTTP** (без TLS), отвечают `400 Bad Request`.
- **[ФАКТ]** `:443` → 200, `<title>UniFi OS</title>`. `:7443` → `302` на `/protect`.
  `:7445` → `Server: Media Server (www.ui.com)` (404 на `/`).
- **[ВЫВОД]** Разделение по назначению (общее знание о UniFi, требует сверки с документацией вендора):
  - **Штатные для UniFi Network:** `:8080` — inform-порт устройств (исторически без TLS),
    `:8443` — веб-UI сети, `:8843` — HTTPS гостевого портала, `:8880` — HTTP гостевого портала.
  - **Штатные для UniFi Protect:** `:7443` — веб-UI Protect, `:7445` — медиасервер.
  - **Порты семейства Protect/UniFi OS (7441, 7442, 7444, 7446, 7447, 7451, 7550, 7552, 7600, 7888,
    11083, 12301, 12443, 12445, 12812, 20201):** отвечают, но **назначение по факту не установлено**
    (без авторизации молчат). Сверить с документацией вендора / списком служб в UniFi OS.
  - `:199` — ответ `41 01 02`; **не идентифицирован** (в общем случае порт 199 связан с SNMP-мультиплексированием,
    но это **[НЕ ПРОВЕРЕНО]**).
- **Критичность:** 🟡 средняя. Проблема не в том, что порты открыты (это норма для консоли), а в том,
  что **поверхность управления большая**, и часть её — **plain HTTP**.
- **Что делать:** отключить неиспользуемые сервисы (Protect/Media, если не нужны); не публиковать эти
  порты наружу; ограничить доступ к 443/7443/8080 доверенными адресами/VLAN; следить за обновлениями.

### C5. Windows-ПК 10.20.30.141: SMB/NetBIOS/RPC открыты на весь LAN

- **[ФАКТ]** Открыты **135 (RPC), 139 (NetBIOS), 445 (SMB)**; в широком проходе дополнительно
  2008, 6045, 7680, 27080, 49664–49668, 49721, 50128, 64881 (динамические RPC-порты).
- **[ВЫВОД]** Это стандартный профиль Windows-ПК, но он даёт атакующему, уже находящемуся в LAN:
  - **SMB (445)** — вектор червеобразного распространения (классический пример класса — EternalBlue/
    WannaCry 2017; применимость конкретного эксплойта **не проверялась**), кража NTLM-хешей
    (responder-атаки), доступ к шарам;
  - **NetBIOS (139)** — устаревший и не нужный в современной сети протокол, дополнительная поверхность;
  - **RPC (135 + динамические)** — движение по сети (lateral movement), удалённое управление.
- **[ФАКТ]** Версия Windows и состояние патчей **не установлены** (сканирование только TCP connect).
- **[НЕ ПРОВЕРЕНО]** Наличие SMBv1, состояние SMB signing, наличие открытых шар без пароля.
- **Критичность:** 🟠 средняя (в домашней сети; при наличии соседей по Wi-Fi — выше).
- **Что делать:** закрыть 139/445 на файрволе Windows (или в правилах UDM), включить **SMB signing**,
  **отключить SMBv1**, изолировать ПК в отдельный VLAN/SSID, не держать общие ресурсы без пароля.

### C6. ~12 устройств Apple с открытым 62078 (iOS lockdown) и 49152

- **[ФАКТ]** Порт **62078** открыт на: .9, .14, .21, .45, .75, .78, .81, .148, .153, .156, .176, .221,
  .223, .227. Порт **49152** — почти на всех из них, кроме .75 и .223.
- **[ВЫВОД]** 62078 — это **usbmuxd / iOS lockdown**, то есть устройства разрешают Wi-Fi-синхронизацию
  (iTunes/Finder «Синхронизация по Wi-Fi») и/или доверительное спаривание по сети.
- **[ВЫВОД]** Риск: это служебный сервис, лишняя поверхность; при **доверенном спаривании** с чужим
  устройством возможен доступ к части данных/резервным копиям. Точная модель угрозы зависит от iOS
  и от того, спарено ли устройство с кем-либо — **не проверено**.
- **Критичность:** 🟡 низкая–средняя.
- **Что делать:** на iPhone/iPad отключить «Синхронизацию по Wi-Fi» (Настройки → Основные → AirDrop и
  Handoff/«Синхронизация по Wi-Fi»), либо изолировать личные устройства в отдельный SSID/гостевую сеть.

### C7. 10.20.30.93:7447 — порт отвечает, сервис не идентифицирован

- **[ФАКТ]** TCP-порт 7447 на .93 принимает соединение, но по протоколу молчит (нет баннера).
- **[ФАКТ] Дополнительное опознание (добавлено позже):** порт не отдаёт приветствия (тишина 6 с);
  на `HTTP`, `HTTP/2`, `RTSP` и случайные байты — **сразу закрывает соединение без ответа**;
  на обычный TLS-ClientHello отвечает **`sslv3 alert handshake failure` (alert 40)** — и с клиентским
  сертификатом, и без, при TLS 1.2/1.3, с разными cipher-наборами и с SNI; при `-tls1_2` по умолчанию —
  `errno=104` (reset). Вывод: это **не HTTP и не обычный HTTPS**, а сервис с собственным бинарным
  протоколом/рукопожатием, который отбрасывает всё «не своё». Для сравнения: на `10.20.30.1:7447` TLS
  вообще не отвечает (timeout) — то есть поведение `.93` и UDM **не идентично**.
- **[ВЫВОД]** Порт `7447` входит в блок `7441–7447`, который на UDM Pro занят приложениями UniFi OS
  (Protect и родственные). Возможно, `.93` — устройство той же экосистемы, но **подтверждения нет**.
- **[НЕ ПРОВЕРЕНО]** Что это за устройство и сервис. MAC/OUI неизвестны (нет ARP).
- **[ВЫВОД] Хорошая новость:** сервис не разговаривает с неаутентифицированным клиентом — обычный
  сканер/браузер/`openssl s_client` не получают ни данных, ни баннера. Это снижает поверхность,
  но **не заменяет** обновление прошивки и изоляцию.
- **[ВЫВОД]** Порт 7447 встречается и на UDM Pro (там он в семействе Protect) — возможна связь с
  UniFi-экосистемой, но **подтверждения нет**.
- **Как идентифицировать:** сверить список клиентов в UniFi OS (Client Devices) по IP .93, проверить
  MAC/OUI в UI, сопоставить с известными устройствами; при наличии доступа — точечно проверить баннер
  этого порта (только своя сеть, без подбора паролей).
- **Критичность:** 🟡 не проверено (потенциально неизвестный сервис в LAN).

### C8. DNS на UDM: локальные имена не резолвятся

- **[ФАКТ]** DNS `:53` на 10.20.30.1 отвечает, но **PTR-запросы → NXDOMAIN**, SOA = `localhost. nobody.invalid.`
  (заглушка). Единственное полученное PTR-имя — `iPhone` для .21.
- **[ВЫВОД]** Локальный DNS не ведёт обратную зону → **имена устройств не резолвятся**. Последствия:
  хуже инвентаризация, часть сервисов не находит устройства по имени, сложнее диагностика, часть
  «дружественных имён» недоступна.
- **Критичность:** 🟢 гигиена (не уязвимость, а неудобство/ограничение наблюдаемости).
- **Что делать (если нужно):** включить/настроить локальные имена в UniFi OS (DHCP-имена/локальный
  DNS-резолвер), либо использовать статические записи.

### C9. Отсутствие сегментации

- **[ФАКТ]** В одной подсети 10.20.30.0/24 находятся: шлюз управления (UDM Pro), Windows-ПК с SMB/RPC,
  ~14 личных Apple-устройств с открытым 62078, AirPlay-приёмник и неизвестный узел .93.
- **[ВЫВОД]** Любое скомпрометированное устройство (телефон, приставка, ПК) оказывается **в одной
  L2-сети с плоскостью управления** консолью. Нет барьера между «личным/IoT» и «управлением».
- **Критичность:** 🟠 средняя (архитектурная).
- **Что делать:** завести **гостевую сеть** для IoT/личных устройств, включить изоляцию клиентов,
  вынести управление в отдельный VLAN, разрешить доступ к консоли только из доверенного сегмента.

### C10. Нет данных о Wi-Fi-шифровании

- **[НЕ ПРОВЕРЕНО]** WPA2/WPA3/SAE, **WPS**, **PMF (802.11w)**, список SSID, наличие гостевого SSID,
  каналы и ширина — **не проверены** (нет Wi-Fi-адаптера и нет доступа в UniFi OS).
- **[НЕ ПРОВЕРЕНО]** Открытые/слабые сети в эфире, скрытые SSID, «один пароль на всё».
- **Что именно проверить в UniFi OS:**
  - **Settings → WiFi → (каждая сеть) → Security Protocol** — должно быть WPA2/WPA3 (или WPA3/SAE);
    не должно быть WEP/открытой сети/TKIP.
  - **PMF (802.11w)** — включить (Required для WPA3, Optional/Required для WPA2).
  - **WPS** — выключить.
  - **Settings → Networks** — наличие гостевой сети + **Client Isolation**.
- **Критичность:** ❓ неизвестно до проверки. Достоверных выводов о слабости Wi-Fi **нет** — именно
  поэтому здесь не ставится «красный» флаг.

## D. Как устранить (пошагово, без применения)

> Пользователь просил **ничего не менять**. Поэтому ниже — «что сделать, если/когда решишь», без
> выполнения. Порядок — по приоритету.

### D1. Обновить прошивку UDM Pro (приоритет 1)

1. **Где:** UniFi OS → **Settings → System → Updates**.
2. **Перед обновлением:** сделать бэкап конфигурации (UniFi OS → System → Backups) и убедиться, что
   есть доступ к консоли локально (не только через интернет).
3. **Как:** применить доступное обновление; после — дождаться полного запуска сервисов.
4. **Проверка, что риск закрыт:** повторить `GET /api/system` → `deviceState` **не** `updateAvailable`;
   сверить версию с последней в бюллетенях вендора.
5. **Оговорка:** прошивки скачиваем/устанавливаем **только вручную из доверенного источника**.

### D2. Снизить информационную утечку `/api/system` (приоритет 4)

1. **Где:** поведение эндпоинта задаёт вендор — напрямую отключить нельзя.
2. **Что реально сделать:** не публиковать консоль наружу; удалённый доступ — через VPN/WireGuard;
   держать прошивку в актуальном состоянии.
3. **Проверка:** `GET /api/system` без авторизации — зафиксировать, что именно отдаётся; держать под
   контролем список аккаунтов (`isSingleUser:false` → больше одного аккаунта).

### D3. Сертификаты (приоритет 5)

1. **Где:** UniFi OS → Settings → System → (Certificate / HTTPS).
2. **Если есть домен:** выпустить Let's Encrypt-сертификат (требует внешней валидации — в офлайне
   невозможно, потребуется доступ в интернет при выпуске).
3. **Если домена нет:** зафиксировать отпечаток текущего сертификата и не игнорировать предупреждения.
4. **Проверка:** subject/issuer перестали быть пустыми; браузер не ругается.

### D4. Plain HTTP (8080/8880) и поверхность управления (приоритет 3)

1. **Где:** UniFi OS → Settings → System / Network; отключить неиспользуемые сервисы
   (Protect/Media, если не нужны).
2. Ограничить доступ к 443/7443/8080 доверенными адресами/VLAN (Firewall rules).
3. Не публиковать эти порты наружу.
4. **Проверка:** повторный проход по портам 10.20.30.1; набор открытых портов должен сократиться;
   `:8080`/`:8880` больше не нужны в повседневной работе.

### D5. Windows-ПК 10.20.30.141 (приоритет 2)

1. **Где:** на самом ПК — Windows Defender Firewall / «Брандмауэр Защитника Windows».
2. Закрыть входящие **139/445** (и **135**, если не нужен удалённо).
3. Включить **SMB signing**; **отключить SMBv1** (Windows Features → SMB 1.0/CIFS).
4. Не держать общие ресурсы без пароля; изолировать ПК (VLAN/SSID).
5. **Проверка, что риск закрыт:** повторный проход — 135/139/445 не отвечают из других сегментов;
   в правилах Windows видно deny.

### D6. Apple-устройства (62078/49152) (приоритет 6)

1. **Где:** на каждом iPhone/iPad — Настройки → Основные → (AirDrop/Handoff) → **Синхронизация по Wi-Fi**
   выключить, если не нужна.
2. Удалить ненужные доверенные пары (iTunes/Finder).
3. Либо изолировать личные устройства в отдельный SSID/гостевую сеть.
4. **Проверка:** 62078 больше не отвечает с этих адресов.

### D7. Идентификация .93:7447 (приоритет 6)

1. **Где:** UniFi OS → Client Devices — найти .93, посмотреть MAC/OUI/имя.
2. Сопоставить с известным оборудованием; при сомнении — изолировать узел до выяснения.

### D8. Сегментация и Wi-Fi (приоритет 3–7)

1. **Где:** UniFi OS → Settings → Networks (гостевая сеть + Client Isolation), Settings → WiFi (протокол
   безопасности, PMF, WPS off).
2. Вынести IoT/личные устройства в гостевую сеть; управление — в доверенный сегмент.
3. **Проверка:** клиенты в гостевой сети не видят 10.20.30.1:443 и не видят друг друга.

## E. Блокировка

Разбираем два смысла слова «блокировка».

### E1. Что блокировать по нашей инициативе и как

| Что блокировать | Где в UI (путь) | Как проверить |
|---|---|---|
| IoT/личные → LAN (управление) | Settings → **Firewall/Security → Rules** — правило **Block** для гостевой сети в сторону основного VLAN | Из гостевой сети `10.20.30.1:443` недоступен |
| 139/445/135 между сегментами | Settings → Firewall → Rules — Block TCP 135/139/445 между VLAN/SSID | Сканирование из другого сегмента не видит порты |
| 62078/49152 в гостевой сети | Settings → Firewall → Rules — Block TCP 62078, 49152 из гостевой сети в LAN | Порт не отвечает |
| Изоляция клиентов в гостевой сети | Settings → **Networks → (гостевая) → Client Isolation** (или Settings → WiFi → сеть) | Два клиента гостевой сети не пингуют/не видят друг друга |
| WPS | Settings → **WiFi → (сеть) → WPS: off** | В свойствах сети WPS выключен |
| Доступ к 443/7443/8080 консоли | Settings → Firewall → Rules — разрешить только доверенным адресам | Из недоверенного сегмента консоль недоступна |
| Неиспользуемые сервисы (Protect/Media) | Settings → **Applications/System** — отключить ненужные приложения | Порты 7443/7445 больше не отвечают |
| UPnP (если включён) | Settings → **Internet/Security → UPnP** — выключить | Внешние пробросы не создаются |

> Перед любыми правками firewall — бэкап конфигурации. **Не отрезать себе доступ**: правило, которое
> блокирует весь трафик, легко закрывает и доступ к самой консоли. Менять по одному правилу и сразу
> проверять доступность. (По правилам работы: бэкап → правка → проверка → `commit`/reload для OpenWrt;
> для UniFi OS — применить и убедиться, что UI/SSH доступны.)

### E2. Если «что-то блокирует доступ» — как диагностировать

Порядок проверки в UniFi OS:

1. **Insights → Threats / Blocked** — есть ли сработавшие блокировки (IPS/IDS, GeoIP, Ad Block).
2. **Insights → (журнал) / Traffic Logs** — отбрасывается ли трафик конкретного клиента.
3. **Client Devices → (устройство) → Blocked** — не заблокирован ли клиент вручную.
4. **Settings → Firewall/Security → Rules** — нет ли правила Block для этого клиента/VLAN/порта.
5. **DNS Shield / Ad Block / Content Filtering** — не блокируется ли домен/сервис на уровне DNS.
6. **IPS/IDS** — не ловит ли он нужный трафик как «угрозу».
7. **Client Isolation** — не изолирован ли клиент от остальной сети.
8. **На клиенте:** проверить IP/шлюз/DNS, что клиент получил адрес (DHCP), нет ли локального файрвола
   (особенно на Windows — D5), не «залип» ли гостевой портал.

## F. Как получить настоящий Wi-Fi-скан

Wi-Fi-параметры эфира (SSID-список, шифрование, WPS, PMF, каналы, гостевой SSID) **в этом отчёте не
проверены**. Чтобы их получить, нужно одно из двух.

### Вариант 1 — из UniFi OS (предпочтительно)

- **Что нужно от пользователя:** логин/пароль в UniFi OS (10.20.30.1).
- **Пути:**
  - **Settings → WiFi → (каждая сеть):** Security Protocol (WPA2/WPA3/SAE), PMF (802.11w), WPS on/off,
    Guest Network, Client Isolation.
  - **Settings → Networks:** гостевые сети, VLAN, изоляция.
  - **По каждому AP — WiFi Scanner / RF Environment** (в UI точки доступа): каналы, ширина, зашумлённость.
- **Что фиксировать по каждому SSID:** SSID, BSSID, канал, ширина канала, тип шифрования, WPS (вкл/выкл),
  PMF (off/optional/required), уровень сигнала, скрытый SSID (да/нет).

### Вариант 2 — скан с ПК/телефона (только своя сеть)

- **Linux:** `iw dev <iface> scan` (нужны права; только свой адаптер и своя сеть).
- **NetworkManager:** `nmcli device wifi list`.
- **Оговорка:** проверять только свою сеть; чужие сети не сканировать, пароли не подбирать.

## Ограничения этого отчёта

- **Скан только TCP.** UDP-сервисы (SNMP 161, NTP и др.) не проверялись — часть поверхности не видна.
- **Скан изнутри LAN.** Наружная экспозиция (что открыто из интернета на 10.20.30.1) **не проверена**.
- **Без авторизации в UniFi OS.** Настройки (Wi-Fi, firewall, аккаунты, список клиентов) недоступны;
  точная версия UniFi OS **не установлена** (эндпоинт версии вернул 401).
- **Wi-Fi-параметры не проверены** (WPA2/WPA3/SAE, WPS, PMF, список SSID, гостевой SSID) — нет
  Wi-Fi-адаптера и нет доступа в UniFi OS.
- **MAC/OUI неизвестны** для всех устройств, кроме шлюза (нет ICMP/ARP, multicast заблокирован).
- **Нет mDNS/SSDP/Bonjour** → нет «дружественных имён» и точной модели устройств.
- **Идентификация устройств — по набору портов и одному PTR-имени** (`iPhone` на .21) — это вывод, а не
  гарантия. Устройства Apple, ПК и .93 следует подтвердить по UI/наличию MAC.
- **Версии прошивок и CVE** не определялись; номера CVE приводятся только как общеизвестный пример
  класса риска и помечены как «проверить в бюллетенях вендора».
- **Нестабильность при высокой параллельности** — часть хостов «мигала»; окончательный список
  (18 хостов) получен при низкой параллельности, но «мигающие» .68/.73/.101 (и др.) требуют перепроверки.
- Отчёт охватывает **только диапазон 10.20.30.0/24** (свой сегмент); чужие сети не затрагивались.
